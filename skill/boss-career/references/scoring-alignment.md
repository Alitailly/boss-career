# 评分材料、标准与结果的对齐

本机新版评分：先按已确认硬条件过滤，再把候选人材料、个人标准和一批岗位交给模型一次评估。未达标只输出分数和简短理由，合格岗位在同次输出中给出详细评价；关键未知保留为待核实。这里的“不适合”是相对用户需求，不等于岗位本身质量差。

## 先确认评分用候选人材料

用户应能分别审查“我是什么情况”和“我优先找什么”。前者是事实材料，后者是评分标准；简历经历不能代替求职意愿，聊天内容也不会自动进入程序。

1. 读 `GET /api/ai/stage-inputs/matching`，检查 `execution_mode`、`candidate_material`、`criteria`、`thresholds`。一次评分应为 `execution_mode=single_pass`；旧服务没有此值时说明版本差异，不能宣称已经单次执行。
2. 根据实际简历、用户确认的事实与补充信息，整理评分需要的简明材料：身份与资格、技能掌握程度、项目/工作证据、可工作安排、关键未知。删去无关叙述与联系方式，保留判断需要的证据，不编造经历；不能把“不曾提及”写成“不具备”。材料长度按实际内容选择，不要求用户凑固定字数。
3. 在对话中把完整材料交给用户核对。接口返回的 `candidate_material.text` 在未确认时可能只是已保存事实的组装稿，不代表用户已经确认摘要。用户决定采用后再保存 `confirmed=true`；也可先存 `false` 草稿供面板审查。
4. 使用 `PUT /api/ai/scoring-material`，字段为 `text`、`confirmed`、`resume_id`、`source_sha`、`expected_candidate`。后三项取刚读到的 `candidate_material`，不要自编版本或指纹。接口会保存候选人新版本、保留其他事实/个人设置并改绑当前方案。冲突时重新读取，不能强行覆盖。
5. 回读 `candidate_material.ready=true`，核对正文确为采用稿。本机新评分仅发送这段材料，不追加整份简历。换简历、原文或事实资料变化会使材料待重新核对；未经确认或过期时，新评分在模型调用前停止。旧评分不会因此重算。

这个确认不是要求每次调用都再问用户：同一份有效材料可持续复用，相关事实变化时才重新对齐。仅确认材料也不授权全库评分或发送。

## 再确认一份个人评分标准

1. 恢复当前标准、硬条件、候选池分数线，结合实际岗位讨论希望优先做什么、哪些职责吸引或排斥用户、哪些能力差距可以接受。用户指出高分岗位不适合时，从JD与模型理由开始，不要求用户先诊断参数或报出应得多少分。
2. 整理自然语言标准供核对，可按“优先考虑什么／哪些相关性不够／哪些不能接受／如何看待能力差距和未知／评分理由怎么写”分段。标题只帮助阅读；默认不要求逐项权重、分项分值或一套通用分数表。用户主动选择分项方法时可以采用。
3. 将用户决定试用的标准保存为 matching 策略 `content.criteria` 非空文本，沿策略登记、绑定、校验及采用流程更新。登记不等于已生效。回读 `criteria.text` 和 `sections` 中实际系统提示词；共同标准变量渲染失败会报错，不静默换成其他偏好。
4. 用已授权少量、有全文且职责不同的岗位试评，展示材料、标准、JD、分数及理由。`POST /api/ai/preview-stage` 用同一单次评分逻辑，返回样例，不写正式分析/发送队列；仍有模型成本。用户核对岗位、理由和排序后，确认候选池分数线 `plan.runtime.min_score`，再按明确范围执行。

`criteria` 存在时替代旧 `content.stage1.system` 和 `stage2.system`，不会叠加旧个人标准。缺少 `criteria` 的旧自定义策略会把两处原文一并带入同一次请求以保留条件，另附单次评分的执行格式。整理为新版标准前先让用户核对，不能遗漏旧条件，也不能声称程序已自动总结个人偏好。

## 一次评分的实际契约

- 每批一次请求，不再先打初筛分再调用详评。`stage2_min_score` 是遗留字段，新链路不使用；候选池只按 `runtime.min_score` 与硬条件、关键未知核对。
- 新执行配置可放在 `content.evaluation`：`batch`（每批最多6岗）、`jd_limit`、`max_tokens`、`input_char_budget`。未设置时兼容读取旧 `stage1.batch`、`stage2.jd_limit/max_tokens`；旧 `stage1.jd_limit=1200` 不再截短新评分输入。长JD时程序按输入字符预算缩小批次，不为维持批量而额外粗截正文。字符预算是组批参考，不是精确token计费上限。
- `decision=match` 对应符合标准详评；`reject` 为未达标简评；`uncertain` 为关键未知。`status=needs_review/failed/hard_filtered/rejected` 不进入自动写稿候选。`stage=full` 在新结果中只是兼容已有准入接口，是否单次评分看 `evaluation_mode=single_pass`。
- 模型漏回、重复id、无效分数或缺少合格岗位必要评价时，保留失败，不以高分准入，也不自动扩散为整批逐岗重评。按具体失败和授权范围显式重试；输出截断可结合本地记录调整批次/输出预算。
- 少输出能减少输出量，单次执行能避免重复请求材料；不能保证模型内部少思考或保证固定节省比例。账单用量按整批记录一次，不伪造逐岗分摊。

## 面板反馈与历史依据

匹配面板先显示评分用候选人材料及确认状态，再显示个人标准。列表可按符合标准、未达标、待核实、硬条件排除、失败、历史结果筛选，支持跳页及每页20/50/100条。

新模型结果保存当次 `candidate_material`、`scoring_rule`、`input_jd`、`input_versions`。用户质疑分数时，优先读这些实际输入与评分理由，判断是事实缺失、标准不符还是本次输出没有遵循要求。模型理由是可审查的评估说明，不是内部思考过程的还原。旧记录缺少当次材料或规则时明确无法追溯，不用当前文本冒充历史输入。

根据用户具体反馈修改对应输入，再以小样例验证；未经新授权不重评全库、不重写既有文案、不发送。外部Skill依然是用户可选的方法：宿主AI从工作项中恢复已确认材料与个人标准，按外部 work/submit 的实际schema提交；保存策略不等于已安装或本机已执行外部方法。
