# 账号异常与恢复处理

用户说“被风控/封控了”“账号异常”“不能登录/发送”，或任务出现登录、验证码、安全网关、频率限制时，进入此分支。目标是保留记录、减少继续触发的操作、给用户可理解的下一步；账号受限不等于程序代码损坏。

## 先暂停，再用本地证据判断

1. 有明确账号异常、登录失效或平台频率限制时，停止本安装相关平台访问；当前共享控制为安装级，账号异常先暂停全部平台操作。用现有暂停/取消入口处理在跑和待执行任务，检查是否还有采集器或已启用的平台周期任务会继续启动。取消请求已提交不等于已经停止，查看同一任务的终态/在途结果；正常等待共享额度不属于异常，不应重建任务。
2. 已有平台原话、发生时间、账号与任务信息就直接使用；缺项再简短补问。记录提示原文、用户看到提示的时间、平台要求再次登录的时间、当时环节及任务 ID，三种时间/事实分别保存。“请于明天10:52再登录”不能解释成“今天10:52触发了限制”。收集脱敏账号标识，不索要密码、Cookie、令牌或完整私人会话。
3. 只读本地：当前账号、共享暂停、相关任务/采集器、近期请求诊断、发送台账及回复同步结果。具体入口见 [共享平台请求控制](current-integration.md#共享平台请求控制)、[请求变慢时的定位](current-integration.md#请求变慢时的定位) 和 [账号切换与记录归属](current-integration.md#账号切换与记录归属)。没有平台提示时，不能仅因“发不出去”就认定被封；反过来也不能为验证用户说法，再访问岗位、消息或登录接口。
4. 告诉用户哪些是已知事实，哪些只是待验证线索。检查采集、补全文、探活、发送、回读、令牌/登录操作是否叠加，是否有重复进程、重复任务或失败后的重试。诊断中的暂停拦截不等于已发出的请求；日志未覆盖的浏览器/App活动也不能凭空补齐。请求节奏、账号/设备环境和平台策略可能共同影响结果，本地日志通常不足以证明唯一触发原因或平台安全阈值。

| 观察到的情况 | 推荐处理 |
| --- | --- |
| 明确提示账号异常、功能受限或要求某时再登录 | 保持暂停，按官方客户端提示等待、由用户完成验证或联系平台客服/申诉。给出的时间只是允许再尝试的时间，不保证届时恢复。 |
| 登录失效、验证码或身份不一致 | 停止受影响平台任务，用户在官方流程处理；程序不自动解验证码或反复试登录。换号/重登后核对任务身份，原任务不自动接续。 |
| 安全网关/code37、局部接口异常 | 采用当前控制记录对应的暂停范围；没有账号级信号时不宣称整个账号被封。停止该链路重试，不强刷令牌；确认其他链路是否允许，以实际共享控制为准。 |
| 单岗下线、标识失效、资料冲突 | 暂停/跳过该岗位核实，不扩大发送范围，也不把所有任务都判成账号异常。 |
| 正常排队、日额度耗尽、任务未被后台接管，或模型/API错误 | 按任务与本地配置处理。先解释实际原因；模型额度不是 BOSS 风控，缩短平台间隔不能解决它。 |

平台提示与现有暂停记录冲突或证据不足时，保留保护状态并报告缺口；不要为了让界面变绿而清除暂停。

## 受限期间仍可做什么

继续解析/优化简历、调整本地采集条件、对已保存 JD 评分、写稿和审核、查看历史档案、准备面试。模型调用是否可用另行判断。复盘可生成本地快照，但必须展示最近观察时间和待更新数量；读不到回复不记为“未回复”。

用户在官方客户端看到的新回复可作为带来源、时间的补充材料；具体保存能力按当前接口核实，没有补录入口就保留为待录入材料，不能谎称已经写回统计。不会读取另一个账号的会话来填补原账号的数据。

用户提出换账号时，说明简历、规则和草稿可沿用，而会话、发送与回复归属不会迁移；按账号切换指引停止旧任务、核对身份。当前程序不自动轮换账号，不通过换号重置频率/总暂停、重发未决消息或绕过平台限制，也不能承诺另一账号不会受影响。不同求职者使用各自工作区。

## 什么时候修改程序

“账号受限”本身不是修改代码的依据。先给用户一份短结论：已暂停的环节、已知提示、诊断线索、可继续的本地工作、恢复条件。源码参考频率不能当作平台承诺的安全值，更慢也不能保证不会受限。

有证据表明程序仍在暂停后发请求、存在重复任务/进程、隐式重试、逐岗额外读取或身份串用时，再做局部修复。配置问题优先通过已有配置入口调整；不要为了应急重写整条链路。保留发送/回复台账、未决状态、请求历史、暂停记录和用户设置；不通过删文件、清库、重装、更换数据目录或移除保护来“恢复”。

调参或修复时记录改前值、改后值、依据、影响范围和生效方式。先用虚构账号、隔离数据及模拟响应验证：请求数量有界、异常会停止、结果未知不重发、切号不串账。本地验证不能解封账号，也不能代替恢复条件；不拿受限账号连续试验不同频率。未经平台处理与用户明确恢复，修好代码也保持平台暂停。

## 恢复是独立步骤

1. 用户已按平台提示处理，并明确要求恢复相应操作后，再检查本地账号、会话、原任务和未决发送。过去授权自动发送不等于授权自动清除新的风控暂停；仅说“重启程序”也不代表恢复平台操作。
2. 按当前安装已有接口清除需要恢复的那一层暂停，入口见 [共享平台请求控制](current-integration.md#共享平台请求控制)、[后台发送与节奏](current-integration.md#后台发送与节奏)、[回复记录与复盘](current-integration.md#回复记录与复盘)。共享控制与发送/核验/回复控制可能分别暂停，说明实际解除范围；保留历史额度。清除本地暂停不等于平台账号已解限。
3. 先核对已成功、失败、未开始和结果未知的记录。保留已成功结果；未知先对账，不自动补发。换号/重登或旧任务无身份绑定时重新确认并建立新任务，不复活旧批次。
4. 有用户授权的新任务时，以有限范围、串行方式恢复一轮，沿用现有共享节奏，不把采集、补全文、发送和回读同时补跑。范围按用户目标与当前接口能力确定，不为“测是否解封”擅自发送测试招呼或批量访问。再次出现平台限制立即停止，保留新记录并反馈，不循环恢复、重登或加速。

结束时区分“本地已暂停/已解除”“平台状态未知/用户确认已处理”“任务已接管/尚未执行”“实际已发送/结果未知”。说明下一次查看结果的入口，无需让 AI 常驻轮询或用户持续盯着对话框。
