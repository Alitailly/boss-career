# 程序接入

2026-11-02 以本机运行服务的只读契约核对。接口可能更新，每次连接以目标服务为准；这里不保存原作者的城市、学历、关键词或个人路径。

## 找到服务并发现能力

使用用户提供的地址；本地默认候选是 `http://127.0.0.1:8787`。读取 `GET /api/ai/manifest`、`GET /api/ai/capabilities` 和 `GET /api/ai/context`，确认服务身份、活动方案、可执行能力、任务与缺项。`GET /api/openapi.json` 提供请求结构，文档入口 `/api/docs`。只展开当前动作所需的 schema 及引用。

连接后同时检查 `/api/system/health` 的启动模式。`mode=demo` 且 `demo.enabled=true` 表示独立离线体验；按 [离线体验](offline-experience.md) 使用已有虚构 JD，不引导登录或提交平台任务。离线接口会以 `offline_demo` 拒绝在线操作，不能把它诊断为账号失效或尝试解除暂停。

服务未启动时，从用户给出的安装目录查看实际启动说明/脚本，核实是否连带启动采集或旧发送任务，再在授权范围内启动。缺少目录/本地工具时只补问该接入信息。当前 AI 能读 Skill，并不意味着能控制用户本地程序。

新工作区使用 `/api/ai/setup`；新用户从中性默认建立方案，迁移旧个人配置仅用于用户确实要沿用自己的旧配置时。若返回缺少代码目录等问题，按实际缺项处理，不复制作者机器路径。

## 评分模型与 API 配置

先确认执行方式：当前用户 AI 可以读取资料、评分并经 work/submit 回写；程序后台自动评分则需要它自己可用的模型接口。聊天产品里已经登录、订阅或安装了某个 Skill，均不等于程序已经有 API 凭据。若另用程序进行简历解析、优化、写稿等模型工作，同样检查对应执行器是否能调用所需模型。

1. 读取 `GET /api/llm/config` 的 `configured`、`has_key`、`base_url`、`model`；按需核对当前 OpenAPI。已有配置先沿用，不让老用户重新填写。`configured=true` 仅表示必需字段齐全，不代表连通性或评分效果通过。
2. 缺少配置时，说明需要用户选择的服务商提供的 API Key、接口根地址 Base URL 和模型名。当前内置客户端使用 OpenAI 兼容的 Chat Completions 方式，不能把任意聊天网页登录地址当成 API。沿用用户已选服务；未选时再协助选择，实际服务商地址、取 Key 步骤与模型名称以其官方资料为准，不把作者的服务或模型写成强制默认。
3. 引导到“AI 与设置 → 模型与 API → 查看配置指引”（`#/settings?tab=ai`）：填写 Key 与接口地址，拉取模型、选择模型、保存配置、测试连接。优先让用户在本机密码输入框填写 Key；AI 已获授权通过本地配置渠道写入时，用 `PUT /api/llm/config` 保存 `api_key/base_url/model`，回报配置状态而不回显完整密钥。读取接口中的打码值不是可重新导入的有效 Key；只改地址/模型时省略 `api_key`，当前接口留空 Key 也会保留旧值。Base URL 填服务商给出的根路径，程序会追加 `/models` 和 `/chat/completions`。
4. `POST /api/llm/models` 可使用已保存的配置，或用临时的 `api_key/base_url` 拉模型列表；拉取成功不代表已经保存配置。提供方不支持模型列表时，说明限制，核实官方模型名后可以通过配置 API 保存并单独测试；不冒称界面支持手填模型名。
5. 对已保存配置调用 `POST /api/llm/test`，核对响应里的 `ok` 和错误提示。此接口失败时也可能 HTTP200，不能只看状态码。测试会给所选服务发送简短探活文字，可能有少量费用，不需要简历或岗位内容；成功只能说明这次模型调用完成。密钥/权限、余额、地址/模型、网络、限流等错误按实际提示处理，避免连续重试。
6. 接口可用后，按用户已确认的评分方法，对1–3个有全文的岗位做评分样例并展示简历/JD依据，再决定批量运行。实际评分会把相应资料发给选定模型服务；沿用用户授权的材料范围。`POST /api/ai/preview-stage` 可做不落库样例；读执行状态及实际输出，区分保存成功、连接成功、评分可用与效果已被用户认可。模型配置不能替代个人评分标准或策略绑定。

这套模型配置在当前安装中共享，并不按每份个人方案分别保存；内置评分和使用该配置的解析、优化、写稿等环节可能一起受影响。更换模型前说明影响范围，已经开始的任务按实际加载时点核实，不宣称修改会立即替换所有在途调用。当前 API 只允许配置上述三项，采样、输出上限和超时等由程序控制。

## 面板导航与用户反馈

2026-11-04 的界面供用户观察实际输入与输出。Skill 引导你理解工作流、与用户对齐个性化方案并操作程序；面板展示采用内容及结果。查看面板不会自动启动采集、评分、写稿、发送或回复同步。旧安装以实际页面为准。

| 页面 | 位置 | 用户主要看什么 |
|---|---|---|
| 求职总览 | `#/`；旧 `#/workflow` 兼容 | 不重复岗位总量、待评分、待审核招呼语、今日发送与需要关注的问题 |
| 简历与资料 | `#/resume` | 原文、解析建议、当前采用版本；可选基础优化或与你定制、寻找外部 Skill |
| 岗位采集 | `#/tasks` | 新增不重复岗位趋势、当前个人条件与实际平台条件、已启用关键词；“长期抓取记录”按页查看历史 |
| 匹配评分 | `#/match` | 先审查实际候选人材料与确认状态，再看个人评分标准；新版一次评分，按结果类型筛选。硬条件、分数线与执行细节可展开；评分列表支持跳页，详情对照JD和理由；历次记录 |
| 招呼语与发送 | `#/review` | 当前个人事实、写作规则及批量指令；点开正文左右对照写稿实际输入与输出；“待写稿与问题”“发送记录”单独切换；`?tab=pending` 可直接定位待处理 |
| 每日复盘 | `#/feedback` | 回复率与读取覆盖、按原发送日期的变化、逐岗 JD／实际招呼语／已保存回复 |
| 面试准备 | `#/interview` | 当前基础出题模板或已绑定外部方法、对应岗位与已有题库；实际对话模拟在用户 AI 中开展 |
| AI 与设置 | `#/settings` | 默认可展开查看各阶段的当前实际模板；模型/API、手动约束和高级采集配置在各自页签 |
| 本地岗位库／任务记录 | `#/jobs`／`#/activity` | 已保存岗位；后台任务、平台暂停状态与可展开的执行参数 |

“复制面板记录”导出用户自己填写的观察和已显示的记录；“复制当前输入”导出当前读取的模板与条件。复制不生成修改建议、不采用规则、不执行任务。设置与账号页的通用复制不自动附带配置字段或密钥。

用户指出某个岗位“为什么分数这么高／低”时，恢复该岗位 JD、对应分析与采用简历，读取当次已保存的 `scoring_rule`（存在时），再用 `GET /api/ai/stage-inputs/matching` 核对当前实际模板、模板外条件与阈值。区分岗位资料有误、标准不符合用户偏好与模型没有遵循标准，再与用户讨论具体修改。校准仍在你与用户的对话中完成；沿用已有策略保存、绑定、校验及采用流程，回读实际模板并用少量样例验证后再扩大范围。

`GET /api/ai/stage-inputs/{stage}` 的 stage 为 `matching/greeting/interview/resume_revision`，只读本地模板，不调用模型或平台。匹配正文复用执行时的渲染和默认回退逻辑；资料输入模板来自程序实际消费的模板，不能把策略文件里未被消费的 `stage1.user/job`、`stage2.user` 当作本机生效内容。外部方法返回保存的方法内容及外部执行标记，不代表已完成执行。当前模板用于后续调用，运行中的任务和旧结果以各自记录为准。

新产生的本机评分会保留当次 `candidate_material`、`scoring_rule`、实际送入的 `input_jd` 与版本；历史记录没有该字段时明确说明无法追溯，不用当前提示词解释旧分数。标准改变后，重评范围和模型调用由你按用户已确认的任务范围决定，面板刷新不会重评。

### 个人标准的修改与回读

面板的提示词、个人条件和候选人材料提供自然语言阅读版：程序字段以中文标签展示，格式示例与执行原文单独折叠。阅读版用于人工审查，不是另一份已采用标准；用户AI核对或修改时以只读接口返回的原文、当次留存输入和明确的执行原文为准，不将阅读排版反写为新规则。

用户调整偏好时，先恢复当前采用的标准，整理成替换稿，再沿策略登记、绑定、验证、采用流程更新。把新要求写到聊天或另一个旧配置文件，不等于替换了执行标准。评分按 [评分标准的对齐与审查](scoring-alignment.md) 处理；新版 `content.criteria` 是一次评分的个人标准，面板按原文分段展示，完整执行指令仍可展开查看。旧策略缺少 `criteria` 时保留两处原文作为单次请求的兼容输入；整理替换稿需核对全部原条件。先按评分对齐指引确认 `candidate_material`；新评分不追加简历全文，旧详评门槛不再生效。分数线和硬条件由用户结合岗位样例确认，不因修改文案自行改分数，也不默认要求用户分配每项分值。

招呼语先读 `GET /api/ai/greeting-rules`，检查 `parts`、`text` 与 `conflicts`；批量写稿再对照 `GET /api/workflow/prompt-preview` 的 `instruction`。迁移策略可能同时含 `preamble/style/system`，旧 `app_settings.greeting_requirement` 也仍参与合成，不能只检查其中一个字段。修改时把相关要求整理在明确的来源中，回读确认旧要求没有继续叠加；需要语义合并或存在冲突时，将整理稿给用户核对后采用。

2026-11-05 修正了完整重复文本的合成：若某段个人要求已被较早来源完整逐行包含，只传入一次，`deduplicated` 记录被合并段与覆盖来源；独有要求保留。仅语义相似或相互冲突的文本不会被程序擅自合并。批量写稿不再追加固定的170–185字目标，采用合成规则中的个人篇幅要求与硬上限。旧服务需加载新代码才有该行为。

规则回读之后，用实际简历与有全文的岗位对照样例：评分展示分数和依据，招呼语展示实际正文及所引用经历，用户认可的是输出效果。更改规则不会自动重评、重写已审核正文或授权发送；沿用本次任务范围处理后续结果。

采集页区分“进程运行中”与“平台操作暂停”：进程还在不代表搜索或全文请求仍可执行。查看新增趋势时同时核对暂停、任务记录和统计范围，不因新增下降就擅自扩条件或提速。参数按需展开供核对，调整由用户 AI 按已确认规则完成。

优先通过个人方案/API 操作；诊断时按需查看非敏感源码。避免直接修改运行台账或打开含凭据的真实数据库来绕过接口。

## 简历生效版本与恢复原稿

评分、写稿实际使用的是活动方案 `candidate_id` 绑定的资料版本。读取当前方案，再读其候选人和 `resume.resume_id` 对应的简历原文；用 `effective.versions.candidate` 交叉核对。2026-11-03 修复后，`context.active.candidate` 与执行版本一致，`saved_candidate` 单独表示最近保存的资料；`effective.candidate.resume_id` 及 `workflow/control/context.active_resume_id` 可定位实际简历。旧安装版本曾有活动资料显示与方案绑定不一致的问题，连接时按实际返回核对。

用户采用优化稿后又要求恢复原稿时，保留当前求职条件，局部将方案 `candidate_id` 改绑到已保存的原资料，按既有 validate/preview/activate 流程生效；回读实际绑定与原简历 ID。无需重新上传或复制一份原文，也不要把整套旧方案直接覆盖回来而丢掉后来确认的城市、关键词等设置。历史发送材料仍按发送记录恢复。

## 平台筛选与实际生效条件

2026-11-04 接入更新。AI 负责理解自然语言，程序负责把合法选项转换为请求代码，保存和最终搜索请求都要经过校验。

1. 按程序提前整理的可操作配置向用户介绍可选条件。首次了解本程序时可用 `GET /api/filters/conditions` 查看本地目录及 `selection.client/entry/profiles`；已有同版本目录就复用，修改个人偏好无需每轮重读目录。这个接口默认只读本地，不访问BOSS。目录对应电脑网页关键词搜索，不能等同于手机App或整个平台的功能。主动介绍相关实际选项及建议，由用户决定限制哪些；沿用已确认选择。普通、实习和兼职按下表解释。将用户偏好映射到目录中的名称/代码，行业分组用于导航，公司人数范围展开为实际档位。
2. 日常使用目录不自动过期联网；没有用户更新目录时使用程序随附的已核对选项。`catalog_storage` 表明内置/本地来源，`source/degraded/fetched_at` 记录历史核对来源与时间，`source=api` 不表示本次读取访问了平台。平台改版、目录确实不符或明确维护更新时，才使用 `?refresh=true`；手动刷新仍有1小时冷却，最多三个公共元数据请求，无账号Cookie、不重试、间隔至少5秒。这是维护能力，不作为用户日常选条件的必经步骤。
3. 沿用当前个人方案局部修改。城市、行业、规模优先写 `target.cities/industries/company_scales`，选择器使用 `unknown/any/list`；其他平台字段放在 `search.base`。已确认的 target 比旧 base 中同维度的覆盖值优先。空数组不会再根据简历学历或毕业年份自动填回；本人本科/在校不等于只搜索本科/在校岗位。
4. 保存后调用方案 `validate`，启用后回读 `/api/ai/context` 的 `effective.search`。检查 `bases`（全部城市）及 `audit.rows` 的字段、名称、代码、状态、来源。`unknown` 是未确认，`any` 是明确不限；空字段不作为参数发送，可能采用平台默认行为。先向用户展示城市、岗位方向和其他关键边界的实际含义，再启动其授权的采集，不为填满表格擅自缩小范围。
5. 未知代码、拼错的筛选字段、行业组名、把个人日薪直接填进平台薪资档等会报422，修正后再提交。不要去掉有问题的值然后宣称全部条件已生效。真实抓取记录中的 `params.config_snapshot.search` 可核对该次任务采用的条件；直接 `/api/collection/config` 修改只影响该入口，常驻采集器仍从活动方案编译。
6. 多城市由采集器按“每城×每关键词”分别采集、分别记翻页游标，共享原有全日额度与间隔；`base` 只是第一城的兼容字段，不能据此宣称已覆盖全部城市。

面板“我想找什么”区分个人偏好与“实际采集条件（当前方案）”，展示已设置、未设置、明确不限及采集后判断；这是编译条件，不证明运行中的旧任务已切换版本。用户反馈界面与结果不符时，优先让其复制“把采集情况交给 AI”的记录，再核对该次任务快照。职位页“手动采集一次”与系统配置的“手动采集配置”属于单次入口，不自动覆盖 AI 批量采集方案；调整后回读对应入口，不把两份配置混为一份。

2026-11-04 核对了官方网页前端 `job~0/job~1` 与通用、搜索筛选接口；以下结论限于当前网页关键词搜索。实际菜单的逐项点击因界面工具无法确认当前网址而未完成，不能报告为已完成界面实测。

| 求职场景 | AI 应向用户介绍的当前网页条件 | 薪资说明 |
|---|---|---|
| 普通岗位/全职 | 城市、关键词、岗位性质、行业、经验、学历、公司规模、薪资待遇、融资阶段 | 当前返回“不限、3K以下、3–5K、5–10K、10–20K、20–50K、50K以上”；从实际返回选，不自行制造中间档 |
| 实习/校招 | 沿用当前搜索入口实际选项；介绍在校生/应届生经验选项，同时说明它们不等于岗位性质。是否限定学历、身份由用户决定 | 当前没有返回实习专用日薪档，也没有实习 jobType 选项；这是该网页入口的限制。日薪岗位可以出现在结果中，不等于存在日薪筛选。手机端是否相同、是否换算均未验证 |
| 兼职 | 共同条件之外，切换为结算方式（日结、周结、月结、完工结）与兼职时段（实际列表） | 网页切换后移除普通薪资条件；日结是结算周期，不是日薪金额区间，不能替代“100–250元/天” |

融资阶段在关键词搜索的字段集合中启用，兼职分支隐藏；按 `selection.profiles` 判断当前可用字段，不能把元数据出现等同于每个入口都启用。职位类别、区/商圈、地铁已接入关键词搜索，按下一节读取本地目录并配置；期望流不接收这几个字段，程序会明确拒绝，需使用关键词搜索入口。

### 精细数据源筛选

2026-11-05 补齐官方电脑关键词搜索已有的三个维度，`selection.revision=desktop-search/2026-11-05`。首次接入升级版时更新一次已有能力记录，之后复用同版本本地目录。采集面板展示实际采用的名称及可选目录，用户 AI 负责与用户确认、写入方案；不是要求用户手动填写代码。

| 用户可以选择 | 目录入口（普通读取均离线） | 写入活动方案 |
|---|---|---|
| 职位类别 | `GET /api/filters/conditions` 的 `position` 三层树，选择末级；大类和中类用于导航 | `search.base.position`：末级代码数组 |
| 区／商圈 | `GET /api/filters/locations?city=城市代码` 的 `multiBusinessDistrict` | 单城市可写 `search.base.multiBusinessDistrict`；多城市写 `search.city_filters[城市代码].multiBusinessDistrict` |
| 地铁线路／站点 | 同一城市接口的 `multiSubway` | 单城市可写 `search.base.multiSubway`；多城市写 `search.city_filters[城市代码].multiSubway` |

精细位置使用官方网页组合格式：`父级代码` 表示整区/全线，`父级代码:子项代码_子项代码` 表示该区商圈/该线站点，多个父级用逗号连接。接口子选项的 `code` 已包含父级前缀，照目录取用；程序会合并同父级并校验城市和父子关系。网页 URL 的 `areaBusiness` 是位置别名，程序统一写 `multiBusinessDistrict`。用户说某个名称时，先定位目录中的唯一实际选项，重名时补问或展示带父级的候选。

位置目录按城市缓存。内置已核实的职位类别和部分城市位置目录；其他城市 `source=missing` 表示还没保存，不表示平台没有此功能。需要这些选项时，显式调用 `GET /api/filters/locations?city=城市代码&refresh=true` 维护该城市一次：不带账号 Cookie、两次公共元数据请求、至少间隔5秒、无重试、同城市尝试间隔1小时，失败保留旧目录。按需维护当前选定城市，不批量遍历所有城市或并发维护目录。面板轮询、普通 GET、保存配置和启动采集都不自动联网读取目录。

多城市示意（代码取自实际目录，不以此例代替用户选择）：

```json
{"search":{"base":{"position":["100109"]},"city_filters":{"101210100":{"multiBusinessDistrict":"330106"}}}}
```

这表示所有目标城市共用 Python 职位类别，仅杭州限定西湖区，其他城市不因此继承杭州位置。城市本身仍在 `target.cities` 确认。多城市时不能把一份城市位置条件放进共用 base；换城市后需重新确认位置。

保存、预览并激活个人方案后，回读 `effective.search.bases`、`search.audit.rows` 的名称和状态；新任务的 `params.config_snapshot.search` 保留实际条件。直接修改 `/api/collection/config` 只改该入口，常驻采集器仍使用活动方案；新选项已接入采集器写入链路。未启用的新字段不会重置旧游标，实际改变筛选范围后才按新条件记录覆盖。平台条件尽量前置，不能据此保证每条返回都符合 JD 中的个人硬条件。

若后续读取到对应日薪选项，优先使用返回的日薪名称和代码，并核对该入口是否已接入；程序按选项表校验，未把薪资限定为固定的月薪代码。单一岗位性质也从选项表映射，新增已验证的实习选项可直接采用。没有实习专选时不要猜1902；没有日薪档时不要假定平台把日薪乘22折成月薪。原始上下界的数字、单位与档位覆盖都以当前入口返回含义为准。

平台无法表达的硬条件，在用户知情后由采集后的本地规则、模型评分之前判断。常驻采集器 `unscored_with_jd` 已通过本地硬条件检查后才提交评分；明确不合薪资/岗位性质等硬条件的岗位无需模型Token。用户AI另行组织评分时，同样先使用本地条件判断入口；软偏好再交给评分。先用可用的城市、行业、规模等条件减少无效数据，不能以本地兜底为由省略平台选项的介绍和配置。

完成标准是用户要求、保存方案、编译条件与任务快照含义一致；保存成功只证明配置写入，不能据此保证平台返回的每个岗位均符合要求，后续硬条件检查继续保留。

## 薪资条件与生效核对

先区分两个入口：`effective.search.base.salary` 是平台搜索条件，取值以平台筛选契约为准；`effective.salary` 是个人方案的薪资判断，作用于采集后的条件预筛。个人薪资设置不会自动等价转换成平台搜索薪资档。检查用户要求在哪一层生效，并回读相应字段。硬条件提前排除的岗位，不会再靠调整评分权重进入评分。

从 `GET /api/ai/context` 读取活动方案和 `effective.salary`，从当前 OpenAPI 核对可写字段。此版本的个人方案支持：

| 字段 | 含义 |
|---|---|
| `period`、`currency`、`min`、`max` | 周期、币种、上下限；区分实习日薪与月薪，未设置的边界保留 `null` |
| `compare=overlap` | 岗位薪资区间与目标区间有交集即可通过，端点相等也通过 |
| `compare=top` | 岗位薪资**上沿**处于目标上下限内；不是要求整个岗位区间都落在目标区间内 |
| `unknown` | 面议等未知薪资的处理设置；保留或按用户要求修改，并核对实际判断结果，缺失薪资不填成0 |

仅作语义演示，目标范围为100–250元/天时：

| 岗位薪资 | `overlap` | `top` |
|---|---|---|
| 200–300元/天 | 通过 | 排除 |
| 80–120元/天 | 通过 | 通过 |
| 50–100元/天 | 通过 | 通过 |
| 250–300元/天 | 通过 | 排除 |
| 80–90、300–400元/天 | 排除 | 排除 |

以上范围是例子，不是其他用户的默认设置。用户已确认比较方式就沿用；用户只说“薪资范围”且当前含义不明确时，用实际例子确认是否接受部分重叠。用户要求“岗位下限保证不低于某值”等不同含义时，核实接口是否支持，说明与现有模式的差别，不擅自用最接近的模式替代。

保存与核对：

1. 沿用已有方案，局部更新已确认的字段。当前版本 `PATCH /api/ai/plans/{plan_id}` 的示意请求如下；`expected_revision` 填当前活动方案ID，具体格式仍以目标服务契约为准。

   ```json
   {
     "expected_revision": "<当前活动方案ID>",
     "patch": {"salary": {"compare": "overlap"}}
   }
   ```

   仅当用户选择重叠时使用这个示例。上下限或周期有变化时一并写入相应字段，保留其余设置。
2. 对返回的新方案ID调用 `validate`、`preview`，核对实际差异；保存草稿与激活分开。用户已确认并授权使用时，调用该方案的 `activate`，再回读 `GET /api/ai/context` 的活动方案ID及 `effective.salary`。
3. 用 `POST /api/ai/judge` 检验有代表性的合成薪资样例，可指定草稿 `plan_id` 在激活前验证。它做条件判断，不调用评分模型，也不会采集或发送；检查返回中 `id=salary` 的判断，同时向用户说明其他条件可能仍阻断该岗位。
4. 既有规则变更按程序实际的生效边界执行；已有批次可能沿用旧快照。样例不符合已确认含义时，先定位字段映射、版本或实现差异，再执行受影响环节。配置回读和实际样例都符合后，才报告规则已生效。

## 评分队列判读

`GET /api/workflow/sendable` 的 `unscored_todo` 是真正待评分，`unscored_blocked` 是已有全文但被硬条件预筛排除，`missing_desc` 是待补全文。`with_jd - analyzed` 包含预筛排除，不能当作可执行积压；接口缺失时保留未知。

`GET /api/match/analyze/status` 返回实时批次的根级 `done`、`total`、`created_at`、`ended_at`；按实际返回兼容旧版 `progress`。区分批次正在调用模型与空闲等待下一轮采集或半价窗口。

已有JD的真实队列可按当前契约用 `POST /api/match/analyze` 单独发起，或使用程序的后台阶段任务入口，不必等待抓取。沿用用户已确认的评分方法、授权范围与半价判断，先查在途任务避免重复；批次和并发按实际配置与实测选择，不把某次测试的数量写成通用默认。

## 写稿与待发送

`GET /api/workflow/sendable?force=true` 的 `eligible` 是当前可继续处理的准入岗位，`ready` 才是正文已回写、版本与校验符合的待发送岗位，`pending_total` 是仍待写稿/处理的数量。`pending_reason_counts` 按完整待办汇总，`pending` 和 `rows` 各最多展示40条，列表长度不是总数。发送台账已确认发送、结果未知或在途的岗位应排除，重新评分不授予再次投递资格。

此版本的分工是：平时采集器只采集、评分；用户AI发起完整流程时接续写稿，不自动创建常驻补稿任务。用户已委托整批流程或补稿时，由用户AI接续：读取准入清单 → 启动所选写稿方法 → 等待任务结束 → 回读 `ready` 和 `pending`。默认后台写稿可用 `POST /api/workflow/control/tasks`，例如 `{"action":"prepare","limit":6,"confirmed":true}`；`limit` 当前接受1–30，内部按已配置的每批写稿数拆分。可用 `only` 指定岗位，完整请求以当前 OpenAPI 为准。较多待办分批接续，核对在途任务与已尝试岗位，避免反复对失败项烧模型调用。保留当前AI写作、对话校准、外部Skill等方法选择；采用其他回写入口后同样回读实际待发送状态。

创建任务后保存返回ID，在 `GET /api/workflow/control/tasks` 中跟踪同一ID的状态及结果。任务结束不代表每条都成功；比较实际新增就绪数和剩余原因。旧简历、JD、分数等失效稿应按当前资料重写；事实校验失败应先核对，不把未确认的到岗天数、实习时长等写成事实。写稿不发送，也不恢复固定时段发送；只有已有发送授权覆盖这些岗位时才能继续发送接口。

## 共享平台请求控制

用户报告风控、账号不可用或任务出现平台限制时，先按 [账号异常与恢复处理](platform-recovery.md) 暂停、保留现场、读取本地证据并向用户说明，再决定是否需要局部修复或恢复；不要直接从调频或清除暂停开始。

2026-11-04 修改：同一数据目录的任务和进程共用本地节奏控制。参考限制为实际操作发起间隔至少8秒、每分钟最多6次、每10分钟最多40次；既有更长的任务间隔仍保留。包含SDK业务HTTP、消息连接/正文发送、浏览器令牌更新操作、登录检查及显式元数据维护；浏览器内部资源、WebSocket自动心跳和程序外App流量不是逐个受控的请求。参考值不保证平台认可或消除限制。

`GET /api/platform/control` 只读本地状态，返回 `account_paused/paused_scopes` 与参考限制。账号/登录/频率限制持久暂停账号的平台操作；code37持久暂停对应链路。业务SDK的网络/安全网关失败不自动重试或强制刷新令牌，活跃探测和补全文遇到平台限制停止该批。采集器跳过已暂停的平台阶段，继续处理可用的本地队列。

`POST /api/platform/pause` 可指定 `scope=account/search/details/send/chat/token/other`；`all` 按账号暂停。用户已处理平台提示并明确恢复后，调用 `POST /api/platform/resume`，请求 `{"confirmed":true,"scope":"所需范围"}`。`all` 清共享控制的账号与各链路暂停，但保留限额历史；恢复本身不测试平台、不触发发送、不重跑旧任务。旧的核验/回复回读暂停仍需按原来源处理，不能把清一个暂停状态当成所有限制都已解除。

发送一条会涉及多次平台操作，因此20秒条间隔不等于固定每20秒发一条；共享额度不足时由程序等待。用户回来询问进度或出现异常时再读同一任务，不能用新建任务/重启程序重置预算。

## 请求变慢时的定位

用户只需说“发送慢”“采集慢”等现象。AI先问清大致时间或采用最近24小时，读 `GET /api/platform/diagnostics?hours=24&limit=100`，再查已有任务ID的状态；全部是本地查询，不为诊断额外访问BOSS。`hours` 为1–168，`limit` 为1–1000，只限制返回的近期事件数；`by_scope` 汇总所读时间窗内的记录。单日最多读取日志末尾4MiB，`truncated=true` 表示汇总不完整，不能称为全天总数；`skipped_lines` 标示无法解析的行。

记录保存在应用数据目录的 `platform-control/requests-日期.jsonl`，按日追加，跨重启保留，不在这里自动删除。只记录请求链、操作ID、进程号、时间、耗时、结果码和固定原因，不记录凭据、链接参数、简历或聊天正文。原始操作ID是本地追踪号，不等于工作流任务ID，需结合时间、进程和任务阶段定位。

`by_scope` 的 search/details/send/chat/token/other 分别对应搜索、岗位详情（补全文/探活/显式核验共用）、建会话、聊天接口或通道、令牌更新及其他。`attempts` 才是已进入受控操作的次数，`blocked` 是暂停拦截次数，`waiting_events` 是等待开始提示，三者不可相加冒充平台请求量；一次操作也不等于浏览器内部的一次HTTP。

| 观察到的记录 | 含义与下一步 |
| --- | --- |
| `duration_seconds` 高，排队低 | 受控操作本身慢；HTTP响应、消息确认或令牌更新等耗时，先核对具体任务与错误，不靠缩短间隔解决。 |
| `queue_seconds` 高，`wait_reasons.min_gap` 多 | 在等待共享最小发起间隔，定位 `boss_jobs/request_control.py::RequestControl.gap`。 |
| `minute_budget` / `ten_minute_budget` 多 | 在等待共享分钟/十分钟额度，定位同类的 `limits`。先检查是否有不必要的重复任务或平台读取。 |
| `lock_wait_seconds` 高 | 等待共享互斥锁，可能有其他线程/进程执行平台操作；结合进程、时间及其他链路记录排查叠加。 |
| `blocked` 或控制状态已暂停 | 说明暂停原因；处理平台提示后明确恢复。缩短间隔、重启或新建任务均不解决暂停。 |
| 以上不足以解释用户感受 | 查任务自身等待、额度、半价评分时段、待办数量和模型调用。没有平台事件不等于程序卡住，也不等于可以提速。 |

耗时记录自本次升级后才有，旧日志只可看次数和结果，不能补造旧耗时。`queue_seconds` 已包含共享锁等待；各任务时间求和不是用户实际等待的墙钟时长。`wait_reasons` 按每次等待时最强的额度约束归类。等待开始事件只表示当时进入等待，实际耗时在操作结束后写入，不把历史等待事件当成当前仍在等待。中断进程可能只留下开始事件。

任务自身参数定位：采集器从当前有效方案编译配置，`collector.py::load_cfg` / `one_cycle` / 主循环分别使用 `jd_interval`、`activity_interval`、`cycle_sleep_sec`；按当前 `PUT /api/workflow/control/collector` 契约调整，不编辑已废弃的 search.json。采集翻页请求的 `page_interval/interval` 在 `collector.py::collect_pages`；发送的条间隔见 `boss_web/services/deliver_task.py` 的 `_interval`（默认 `boss_jobs/config.py::DELIVER_INTERVAL`），批间隔 `chunk_gap` 从当前 recipe/run 读取并按 settings 契约更新；回复读取本身的间隔在 `boss_web/services/feedback_reader.py::REQUEST_GAP_SECONDS`。先回读有效配置，不能把源码默认值当成用户当前值；任务参数仍会受共享控制约束。

先告诉用户“哪一环慢、证据、建议改哪一项”，再按其请求做局部调整。记录改前值、改后值、原因及生效方式；用相同范围比较改后的新增岗位/完成量、排队和异常，不把额度拉高本身当作优化成功。共享控制当前只有状态、暂停/恢复和诊断接口，没有调频写入API；确需改共享值时修改源码并重启相关服务/采集器，保留暂停与历史。不能宣称接口保存了并不存在的配置。诊断过程不自动解除账号暂停。

## 后台发送与节奏

已审核稿件的整批发送走 `POST /api/workflow/control/tasks` 的 `action=send`，附当前 `approved` 指纹和 `confirmed=true`；范围授权走 `POST /api/workflow/control/authorization/{id}/run`。一次提交一批，间隔和逐条核验由程序执行，不要用聊天工具循环“发一条—等待—再发一条”。接口有单次条数和额度限制，提交数量按当前契约与用户授权，不等于同时并发发送。

任务回执中的 `background.handoff_ready=true` 且 `runner_alive=true` 表示运行中的服务已接管；`chat_required=false`。记录 `id` 和 `background.status_url`，告诉用户可结束对话、稍后从任务及实际发送记录查看结果，然后结束该轮。无需持续 GET 状态来维持任务；这不会让发送更快。可用 `GET /api/workflow/control/tasks/{id}` 在之后恢复。范围授权入口的回执在 `task.background`。没有接管时按回执修复服务，不把“已入队”说成“后台正在发送”。

默认执行器驻留于程序服务进程，与 AI 对话无依赖。可以关闭 AI 聊天和网页，程序服务与电脑需保持运行及唤醒；退出程序、关机或休眠不会继续。完成结果持久化不等于会主动发消息到 AI 聊天，通知能力按宿主实际支持说明。重试提交可用同一 `Idempotency-Key` 防止重复建任务（当前控制接口限即时任务）；仅同一次相同请求复用该键，发送结果未知仍先对账。

即时提交的批次可在程序中依次排队，不因正常等待超过5分钟就过期；明确指定未来执行时刻的任务仍保留错过时段的过期规则。授权有效期、版本、额度和中断待核对仍由执行器检查。这个修复不会复活历史已经过期、取消或失败的发送任务。

2026-11-03 当前参考节奏为 `runtime.chunk=1`、`runtime.chunk_gap=20`：每条一组，完成后至少等待20秒再处理下一条，另加实际发送耗时；服务端逐条发送间隔参考值也为20秒，拆成多个子任务仍受该间隔约束。读 `/api/workflow/overview` 的有效配置核对，不只改旧文件或沿用“5条/180秒”的旧说明。它不是 BOSS 公布的安全阈值，也不表示所有平台请求都相隔20秒。采集、补全文、活跃探测、回复回读分别有自己的节奏；不要为每条发送额外插入实时详情核验。

暂停按来源区分：普通岗位下线、资料缺失或不符，只处理该岗位；可选核验遇到环境校验异常时，仅暂停核验，`read_control.verification_paused=true`，不因此阻断正常发送、评分或采集。真正的账号异常、登录失效或频率限制仍需暂停相关平台操作，不能为完成批次忽略这些信号。先读 `GET /api/deliver/status` 的 `read_control`。用户处理提示并明确恢复相应环节后，调用 `POST /api/deliver/resume`，请求 `{"confirmed":true,"scope":"verification"}` 或 `scope=send`；它只清除指定范围的暂停，不启动或重试任务。不要反复新建批次来代替异常处理。

正常发送只复核已采集资料、当前硬条件、评分所用JD指纹、审核资料与用户冲突标记，不重新访问详情接口。采集和补全文取得详情时同步更新名称、薪资等字段，不增加原采集请求。资料变化或冲突的岗位留待处理，其余合格岗位继续；本地资料不保证平台此刻没有变化，不能把它称为“发送前已实时核实”。

有明确排查需要时才用 `POST /api/jobs/{id}/verify` 显式刷新一个岗位；它不发送，也不授予发送权限。该入口一次只请求一份详情，无自动验证重试，间隔至少取现有 `jd_interval` 与5秒中的较大值；过密调用返回409及等待时间。采集、补全文、发送或常驻采集器运行时会延后，并与回复回读互斥；不要为追求实时性临时加速或反复调用。优先通过原采集链按既定节奏更新资料。`GET /api/jobs/{id}` 的 `verification` 提供最近核验结果。

用户报告平台与本地不一致时，可用 `POST /api/jobs/{id}/conflict`，请求 `{"confirmed":true,"reason":"用户报告的差异","active":true}` 记录并阻断该岗位；相同本地值或回读值不自动消除此标记。冲突核实解决、用户同意恢复该岗位时，以 `active=false` 和解决依据清除，之后仍需正常发送审核。无需坚持要求用户再次提供链接证明。

## 本地资料审查

先用 `GET /api/jobs/{id}/audit` 对照列表薪资、列表最近采到时间、全文保存时间、JD指纹、最近额外核验及当前本地硬条件。此接口不访问BOSS，不解除冲突，也不授予发送权限。列表重新采到不等于全文重新获取；资料较旧是线索，不能直接证明旧资料有错。

区分旧版本遗留记录和修复后新入库岗位；用户已说明历史问题修复时，不把原记录再次当作现版本缺陷的证据。原始列表、评分、发送快照与平台界面无法完整对应时，说明缺少哪一段证据，不用推测补齐。历史高分与“未命中黑名单”均不代表平台当前薪资已经核实。历史分析接口返回当前 `information_conflict`，存在冲突时保持待核实。

正常发送在原有会话对象查询中校验返回的招聘者标识；明确不一致则停止正文发送，可能已尝试建会话，不能直接重试。该检查复用已有响应，不增加逐岗详情请求。

## 账号切换与记录归属

`GET /api/auth/account` 只读本地身份，返回 `sender_account_id`、不透明的 `session_version` 和 `identity_known`，不发送登录或身份探测请求。身份未确认时先正常登录；不能用昵称或脱敏手机号猜测账号。具体安装若缺此接口，说明尚不支持可靠账号绑定，先修复接入，不假装已经隔离。

发送前展示本批账号。`POST /api/deliver/start` 可携带 `sender_account_id`、`sender_session_version` 和逐岗 `application_ids`，服务端核对身份并绑定快照；省略时也会绑定当前本地身份。工作流发送与后台排队入口会自动传递绑定。新记录保存账号、稳定投递标识、岗位材料和实际正文，重试/对账不另算一次成功发送。原有跨账号岗位冷却及未知结果冻结继续有效，换号不自动重发同一岗位。

用户要换号时，先停止并确认原采集器、发送任务已结束，再使用正常登录流程切换。已排队或正在运行的平台任务在账号/会话变化后停止，不能自动转移；同账号重新登录也可能使旧会话绑定失效。需要继续时明确本次账号、范围和额度，提交新任务；旧排队任务或周期任务缺少绑定或绑定失效时应重新创建。评分、写稿、简历和求职偏好可在本地继续使用；不同求职者的简历与偏好应使用各自工作区。

现有安装级请求节奏与暂停不随换号重置，不自动清除账号限制或调用恢复接口。账号分工不是保证安全的方案，也不代表平台岗位标识、推荐和可见性跨账号一致；出现标识无效或资料冲突时暂停该岗核实，不为每个岗位新增强制在线核验。

复盘 `by_account` 分账号展示，`unassigned_sent` 为历史账号待确认数，`unique_jobs` 为独立岗位数；整体 `sent` 是投递记录数，不代表跨账号唯一岗位数。同步只处理当前账号发送的记录。其他账号未登录、受限或未读取时保留旧观察与未知状态，不记为无回复。历史缺少身份依据的记录只保留本地查看，本版本不提供自动归属或批量迁移入口；有明确历史证据时再单独设计追加更正，不直接改原台账。

## 回复记录与复盘

`GET /api/workflow/feedback` 读取本地发送与反馈台账的汇总，不请求BOSS，也不发送。返回 `overall`、`cohorts`、`daily`、`last_checked_at`、`last_sync` 和统计截至时间；新版面板在独立的“每日复盘”（`#/feedback`）展示，发送页提供跳转入口。查询前确认目标安装版本实际有该入口。

- `sent/replied/none/unknown` 按投递标识去重，区分发送账号；缺少标识的旧记录保留原岗位口径并单列归属待确认。`none` 仅表示已读到可辨认会话、暂未观察到对方回复。未知包含未同步、空响应和读取失败。
- `coverage` 是已知状态数/发送数。`reply_rate` 在该范围存在未知时为 `null`；`known_reply_rate` 只在已读子集中计算，不能冒充全量回复率。
- 24/72/168小时表示发送已过去至少这么久的重叠范围，截至当前的累计回复，不是“在这段固定窗口内回复”的比例；`daily` 按原发送日期归组，迟到回复更新原组。不要把今天收到的回复除以今天发送数。

实际回读可由 `POST /api/workflow/control/tasks` 的 `action=feedback` 启动，`limit` 为本次最多检查会话数。同步脚本逐个请求会话，优先处理未读或最久未检查的岗位；发送未满1小时、距上次检查不足6小时的暂时跳过，已回复岗位在间隔后也可更新后续消息。当前参考值不代表所有用户的最佳节奏。每次任务限额不等于当天全部岗位已经读完，应同时看剩余数量和覆盖率。输出本地 Markdown 与 JSON 日报。只查看旧日报不等于完成了今天的同步。每天持续记录还需要真实启用的反馈调度；核对 `/api/workflow/control/schedule` 及宿主调度状态，不把空的任务计划说成正在每日执行。

按岗位查看与恢复材料：

- `GET /api/workflow/feedback/records`：按 `status=all/reply/none/unknown` 筛选，支持 `offset/limit` 分页，返回公司、岗位、发送与检查时间。
- 列表返回 `record_id`、`sender_account_id`、`application_id`；使用 `GET /api/workflow/feedback/records/{record_id}` 读取指定投递的本地JD、实际招呼语、已保存回复及来源。旧 job_id 仅在可唯一定位时兼容；多条记录时先让用户选择对应账号/发送记录。查看不会重新爬取平台。
- 新的工作流发送在发送意图中保存当时JD快照；旧记录无快照时，返回当前本地JD并明确标记版本缺口。没有实际发送正文时保留缺失，不从后来生成的稿件推断。旧回复可能只剩短摘要；新同步保留实际读到的消息并按消息ID合并，不能声称平台全量聊天已完整归档。
- 同一招聘者关联多个已投岗位且无法确认回复归属时，消息可以留存，但岗位回复状态保留未知，交由用户和AI结合内容核实。

风控与恢复：实际平台读取之间当前至少间隔5秒，回复回读串行进行，检测到采集、补全文或发送正在运行时延后；这些是参考控制，不保证消除平台风险。反馈读取不自动刷新验证令牌重试；遇到账户异常、频繁请求、登录/验证问题会停止并持久化暂停。`GET /api/workflow/feedback` 的 `read_control` 可核对暂停原因；先让用户处理平台提示，用户明确同意恢复后才调用 `POST /api/workflow/feedback/resume`，请求 `{"confirmed":true}`。恢复仅清除本地暂停状态，不会自行启动新一轮同步；不可用反复恢复来绕过限制。空响应同样作为未知并停止本轮，不靠并发或加频率来补数字。

2026-11-02 此安装实例曾遇到账户异常提示，以及历史消息接口成功却返回空对象；这只能记未知。程序修复了漏算已记录回复和覆盖展示，但不能据此宣称平台回读已经恢复。遇到这些信号暂停连续回读，向用户说明可读覆盖和原因；通道恢复或采用用户提供的实际反馈后再更新，不通过增加频率获取看似完整的数字。这个实例的历史故障不是所有用户的固定状态，操作时以当前同步结果为准。

## 当前版本需要知道的限制

2026-11-03 修复并复测了空白工作区的后台提交：`POST /api/workflow/control/tasks` 从有效方案读取资料版本，不再要求存在旧 `greeting/profile.json`；采集、匹配、写稿、发送和反馈可按各阶段条件提交。无旧文件的隔离流程已验证队列接管与模拟发送，未用真实平台发送验证。旧安装若仍报缺 profile 文件，按未提交成功处理，升级或修复该入口；不复制原作者配置或创建占位文件冒充已修复。

前轮独立测试发现：发送授权暂停后，同一子批次尚有后续消息可能继续发出。首次使用某安装版本的批量发送前，检查该问题是否已有修复及验证；未修复时限用已验证的一条消息一个子批次路径，且先核实参数确实传到执行层。无法确认时，继续准备与校准，暂停实际发送。不要把“已收到暂停请求”描述成已经停止。

前轮还发现部分旧控制接口读取旧配置，与 AI 活动方案可能不一致；优先使用 AI context，执行结果需核对实际条件。此类限制按受影响动作处理，不阻塞简历、条件建议、评分/文案校准和模拟面试。

2026-11-02 查看默认出题器：其输入模板包含 JD、简历和匹配分析，没有单独的“实际发送招呼语”字段。针对受邀岗位练习时，由当前 AI 按需从对应发送记录取回实际正文，与 JD、关联简历共同使用；不能把传入 job_id 等同于已加载全部三类材料。读取不到发送正文或历史版本时，说明缺项并向用户补问相应材料。


### 招呼语的阶段衔接与审查

`GET /api/ai/greeting-inputs/{job_id}` 只读本地数据，展示留存的写稿请求、可引用事实和引用编号、岗位摘要/JD摘录、匹配点、写作规则及成稿。可带 `analysis_id` 定位关联分析，带 `text_sha`（正文SHA256前16位）定位某版文案，避免把最新稿输入冒充旧稿依据。读取不会写稿、发送、同步平台或调用模型。

批量写稿实际使用评分生成的岗位摘要/匹配点、JD原文摘录和个人可引用事实；不是把评分模型的每句话当作真实经历，也不是默认整份JD和简历都传入。新版桥接器留存实际组装的输入，台账记录路径、校验指纹与引用编号；符合标准的评分结果才接续写稿，关键未知与失败先保留待处理。

用户质疑文案时，对照本条实际写稿输入与输出，定位事实缺失、岗位摘要失真、匹配点不适合或写作规则不符，再与用户调整对应环节。不要只改文风掩盖上游问题。历史稿/其他生成渠道没有留存实际输入时会明确标缺失；“当前关联评分”“当前岗位全文”“当前写作规则”只能作参考，不能声称它们是当次输入。面板不承担自动给建议或替用户采用新规则的职责。
