# 离线体验与采集不可用时的继续方式

适用：用户想先测试使用流程；服务处于 `mode=demo`；或账号受限、采集不可用，使真实求职流程卡在获取 JD。完成标准是用户看到有来源标记的岗位输入、实际评分或草稿，并能继续给出反馈，而非把采集状态改成成功。

## 选择可用材料

1. 有账号限制、验证码或平台异常，先执行 [账号异常与恢复处理](platform-recovery.md) 的暂停和本地检查。用户已提供限制事实就直接使用，不发平台请求来证明它，也不反复尝试登录或采集。
2. 从本地岗位库检查是否有适合本次目标的完整 JD。已有真实 JD 可直接用于评分、写稿、审核和面试准备；展示采集时间及资料缺项。只有列表卡片时说明正文缺失，不自动访问平台补全文。
3. 用户以流程体验为目的且没有可用完整 JD，采用下述独立离线模式。已明确委托测试时说明选择后继续；普通求职用户先简短介绍这个选择，接受其继续处理真实资料或等待的决定。

## 启动独立离线体验

在用户提供的本地仓库 `program/` 目录运行：

```text
python -m boss_web --mode demo --port 8792
```

使用该环境实际安装依赖的 Python。程序不自动复制原工作区、登录态、模型密钥或个人资料。它使用独立的 `data-demo/`，提供 5 份虚构 JD；首次没有候选人或个人方案。可用 `--demo-dir 新的空目录` 建立另一份体验，已有非示例目录会被拒绝。旧版本不支持该参数时如实说明，继续在聊天中用明确展示的样本讨论，不向真实数据库直接插入虚构岗位。

保留原服务地址与暂停状态，读取新服务实际打印的地址，再检查：

- `/api/system/health` 的 `mode=demo`、`demo.enabled=true`、`demo.platform_access=disabled`；
- `/api/ai/context` 的工作区 ID、活动资料和方案；
- `/api/jobs` 的 `demo-` 岗位 ID、带“示例”的公司名及完整正文。

不通过启动采集或发送来检验保护。端口可能顺延，不能继续把离线任务写到原服务地址。

## 把体验接到有用结果

向用户简短交代：“这次用虚构 JD 测试后续流程，账号保持暂停；不会采集、发送或同步回复。”展示将使用的样本，至少包括一个可能相关、一个明显不合适、一个信息不完整的岗位，并标明它们不是市场证据。

沿用对话中已确认的简历处理选择、事实和偏好。需要在独立工作区使用这些资料时，通过已有资料、方案接口保存并回读；保留原工作区，不要求用户把已回答的城市、方向和薪资再回答一遍。用户没有授权采用的评分标准或文案不能补成“已确认”。

之后沿原 Skill 的评分与招呼语校准步骤进行：

1. 核对候选人材料、目标和当前使用的方法。离线体验同样允许原样使用简历。
2. 从所选示例 JD 产生实际评分与依据，对照相关性、硬门槛和未知信息；让用户反馈判断是否合理。
3. 根据个人事实和示例 JD 生成草稿，展示对应依据，修改并通过现有接口保存、回读。文案明确属于示例岗位，不发送。
4. 用户要求面试准备时恢复这个示例 JD 开始练习；回复与复盘只能展示已有本地记录或说明尚无数据。

程序后台评分/写稿依赖单独的模型配置；也可以由当前对话 AI 通过 `/api/ai/work` 与 `/submit` 完成，按当前 OpenAPI 的输入指纹和结果结构提交。缺后台 Key 不等于不能继续聊天校准。接口不能保存时，明确哪些仅在聊天中完成，不能把它们报告为已入库。

## 结束与恢复

报告本次实际验证的环节、使用的样本、已保存结果和局部缺口。真实采集、投递成功、招聘者回复及市场覆盖保持“未验证”，不补造数据。离线实例的“恢复暂停”入口不能开启平台操作，也不自动恢复原实例。

用户之后明确要求恢复真实求职时，回到原服务，按账号恢复指引核对限制处理、身份、原任务和未决发送；另建已授权的新任务。认可示例效果可以用于讨论真实规则，不能直接把示例岗位或演示记录迁成真实投递记录。
